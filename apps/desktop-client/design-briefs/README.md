# 설계 문서(Design Brief) — 분석·설계와 구현의 분리

이 디렉터리는 **분석·설계를 맡은 쪽이 작성하고, 구현을 맡은 쪽(현재 Desktop
Client는 Codex)이 읽고 그대로 구현하는** 작업 지시서를 담는다.

## 파일 구조 — 설계 문서와 구현 보고는 **반드시 분리한다**

```
design-briefs/
├── README.md                        ← 이 파일 (형식)
├── NNN-<slug>.md                    ← 설계 문서 (설계자가 씀)
└── reports/
    └── NNN-<slug>.md                ← 구현 보고 (구현자가 씀, 같은 이름)
```

작업 하나에 설계 문서 하나, 구현 보고 하나다. 파일명은 같고 폴더로 구분한다.

### 설계 문서 없이 직접 지시받은 작업도 반드시 보고를 남긴다

대화로 바로 지시받아 설계 문서가 없는 작업이라도 **구현 보고는 파일로 남긴다.**
이때는 `reports/YYYY-MM-DD-<slug>.md`로 만들고, 보고 첫머리에 **받은 지시를
그대로 적는다**(요약하지 말고 지시 원문을 인용한다).

이유: 검증하는 쪽은 무엇을 시켰는지 모른 채 결과만 본다. 보고가 없으면 전체
`git diff`를 훑어 무엇이 왜 바뀌었는지 역추적해야 하고, 그러면 "지시받아 한 일"과
"스스로 판단해 한 일"이 구분되지 않는다. 실제로 이 저장소에서 그런 일이 있었다 —
설계 문서 001 범위는 파일 3개였는데 22개가 바뀌었고, 그중 어디까지가 지시였는지
보고에 없어 확인에 시간이 걸렸다.

한 번에 여러 지시를 받아 함께 작업했다면 보고 하나에 지시를 모두 나열하고,
어떤 변경이 어떤 지시에서 나왔는지 연결해 적는다.

**구현 보고를 설계 문서에 덧붙이지 마라.** 다음 이유 때문이다:

- 설계 문서는 **지시서**다. 지시가 그대로 남아 있어야 "무엇을 시켰는가"와
  "무엇이 나왔는가"를 나란히 두고 대조할 수 있다. 보고가 뒤에 붙으면 지시를
  다시 읽을 때마다 결과를 헤치고 들어가야 한다.
- git diff가 섞인다. 지시가 바뀐 것인지 결과가 추가된 것인지 구분되지 않는다.
- 한 설계 문서에 **보고가 여러 번** 달릴 수 있다(반려 후 재작업, 부분 구현).
  파일이 하나면 이력이 뭉개진다.
- 검증하는 쪽은 지시서만, 구현하는 쪽은 보고만 고치므로 충돌하지 않는다.

설계 문서를 수정해야 하면(요구 변경·오류 정정) 설계자가 설계 문서를 고치고,
구현자는 보고에 "설계 문서 vN 기준" 식으로 무엇을 보고 작업했는지 남긴다.

## 왜 이 형식인가

설계 문서를 아무리 잘 써도 **구현 결과를 검증하는 단계는 대체되지 않는다.**
이 저장소에서 실제로 있었던 일이다 — 구현자가 "테스트 전부 통과"를 정직하게
보고했지만, 검증해 보니:

- 변조(tamper) 테스트가 "변조 후에도 파일이 열리도록" 바이트를 골라 실제
  공격면을 비껴갔다.
- 패키지 무결성 검사가 15개 파일 중 4개만 덮고 있었다.
- 화면에서 오류를 삼키는 `if (!res.ok) return;`이 들어가 에러 상태가 통째로
  사라졌다.

**전부 그들의 테스트는 초록불이었다.** 그래서 이 형식은 "무엇을 만들지"보다
**"무엇으로 됐다고 판정할지"**에 무게를 둔다. §5와 §6이 이 문서의 핵심이고,
나머지는 그것을 위한 배경이다.

## 작성 규칙

- **분량은 필요한 만큼.** 다만 배경 설명보다 판정 기준이 길어야 정상이다.
- **확인하지 않은 경로·함수명·수치를 쓰지 않는다.** 설계자가 실제 코드를 열어
  확인한 것만 쓴다. 틀린 경로 하나가 구현자를 엉뚱한 곳으로 보낸다.
- **모듈 규칙을 여기에 복사하지 않는다.** `apps/desktop-client/CLAUDE.md` 등
  모듈 문서를 가리키고, 이 작업에만 해당하는 것을 쓴다.
- 구현자가 스스로 판단해야 할 것과 판단하면 안 되는 것을 구분해서 적는다.

## 고정 형식

```markdown
# NNN — <작업 제목>

대상 모듈: <경로> (<모듈 ID>)
작성자/일자: <설계자> / <YYYY-MM-DD>
선행 조건: <이 작업 전에 끝나 있어야 하는 것. 없으면 "없음">

## 1. 문제

무엇이 잘못되어 있는지. **재현 방법과 관찰된 증상**을 구체적으로.
"개선한다"가 아니라 "지금 X인데 Y여야 한다"로 쓴다.

## 2. 원인

코드 수준의 근본 원인. 파일:줄 번호로 지목한다.
확인하지 못했으면 "추정"이라고 명시한다.

## 3. 변경 범위

| 파일 | 무엇을 | 신규/수정/삭제 |
|---|---|---|

계약(`packages/schemas`, OpenAPI, IPC 채널)이 바뀌면 별도로 표시한다.

## 4. 설계

어떻게 고칠지. 구현자가 재설계하지 않아도 되게 충분히 구체적으로 —
함수 시그니처, 타입, 상태 흐름. 다만 **줄 단위 코드를 받아쓰게 하지는 않는다**
(그럴 거면 설계자가 직접 고치는 게 빠르다).

## 5. 깨면 안 되는 것 (불변식)

| 불변식 | 왜 | 증명하는 테스트/확인 방법 |
|---|---|---|

보안·계약·기존 동작 중 이 작업이 건드릴 위험이 있는 것. **각 항목마다
그것이 지켜졌음을 어떻게 확인하는지**를 반드시 함께 적는다. 확인 방법이
없는 불변식은 불변식이 아니라 희망이다.

## 6. 완료 판정

### 6.1 실행할 명령과 기대 결과
```
$ <명령>
<기대 출력 — 수치까지>
```
기준선 수치를 반드시 적는다(예: 테스트 349개 통과). "통과하면 됨"이 아니라
"몇 개가 통과해야 하는지"를 적어야 조용한 누락이 드러난다.

### 6.2 반드시 존재해야 할 테스트
새로 추가되어야 하는 테스트 케이스를 이름과 검증 내용으로 지정한다.
자동 테스트로 증명 불가능한 것은 그렇다고 명시한다.

### 6.3 눈으로 확인할 것
자동 테스트가 못 잡는 것(레이아웃, 실제 화면 동작). 구체적인 조작 순서와
기대 화면을 적는다. **이 모듈은 렌더링 테스트가 없어 UI 변경은 여기서만
검증된다.**

## 7. 범위 밖

이 작업에서 하지 말 것. 인접한 문제를 발견해도 여기 적고 넘어간다.

## 8. 열린 질문

구현자가 임의로 정하면 안 되는 것. 없으면 "없음".
```

## 구현자가 끝낸 뒤 — 구현 보고

**설계 문서를 수정하지 말고**, `reports/<설계 문서와 같은 이름>.md`를 새로 만든다.

```markdown
# 구현 보고 NNN — <작업 제목>

설계 문서: [`../NNN-<slug>.md`](../NNN-<slug>.md)
        (설계 문서가 없으면 "없음 — 직접 지시")
구현자: <누구> / 일자: <YYYY-MM-DD>

## 받은 지시

설계 문서 외에 직접 받은 지시가 있으면 **원문 그대로** 적는다.
요약하거나 다듬지 않는다 — 검증하는 쪽이 "시킨 것"과 "판단한 것"을
구분할 수 있어야 한다. 설계 문서만으로 작업했으면 "설계 문서 NNN 그대로".

## 무엇이 어떻게 됐나

지시별로 실제 결과를 적는다. 변경한 파일과 그 이유를 연결한다.

| 파일 | 무엇을 | 어느 지시에서 | 신규/수정/삭제 |
|---|---|---|---|

## 실행 결과
설계 문서 §6.1 명령의 **실제 출력**(기대치가 아니라 실행 결과).
실패가 있으면 숨기지 말고 그대로 적는다. 실행하지 않은 것은 "미실행"이라고 쓴다.

## 추가한 테스트
§6.2 항목을 어디에 어떤 이름으로 추가했는지.

## 눈으로 확인한 결과
§6.3의 항목별로 무엇을 보았는지. 확인하지 못했으면 그 이유를 적는다
(예: "브라우저 확장이 연결되어 있지 않아 미확인").

## 설계와 다른 부분
설계 문서와 다르게 구현한 것과 그 이유. 없으면 "없음".

## 범위 밖으로 남긴 것
발견했지만 §7에 따라 손대지 않은 것.
```

**"전부 통과했습니다"만 적힌 보고는 반려한다.** 무엇이 몇 개 통과했는지가
없으면 검증하는 쪽이 확인할 방법이 없다. 마찬가지로 "§6.3 확인함"만 적고
무엇을 보았는지 없는 보고도 반려한다 — 이 모듈은 렌더링 테스트가 없어
육안 확인이 UI 변경의 유일한 증거다.
